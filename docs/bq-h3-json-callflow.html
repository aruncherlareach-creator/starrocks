BigQuery External Catalog — End-to-End Call Flow

What this gives you

Query BigQuery datasets directly from Ontology DB SQL — no ETL, no data movement, no duplication. Analysts use familiar SQL against live BQ data (GKE datasets, GKE resource usage, cost tables, etc.) while Ontology DB handles predicate pushdown, column pruning, and parallel Arrow stream reads. Combine with internal Ontology DB tables for cross-source JOINs in a single query.

Transparent Query Rewrite: BigQuery → Ontology DB MV
Define a Materialized View over a BigQuery external table. Ontology DB automatically rewrites matching queries to use the local MV cache — zero BigQuery API calls, sub-millisecond latency — without any change to the user's SQL.

How rewrite works

1
Define MV over BigQuery table
MV stores aggregated BQ data locally. Refreshed on schedule or manually.
2
User runs any matching query against BQ table
Standard SQL against bq_catalog.dataset.table — no special syntax.
3
Optimizer checks MV rewrite candidates
Tests whether predicates, projections, and aggregations can be served from any active MV.
✓
Rewrite: local MV — zero BigQuery call
Millisecond response from Ontology DB BE regardless of BQ table size.
↓
No match: falls back to live BigQuery scan
Normal BQ Storage API path — transparent to user.

💰 Cost reduction
BigQuery charges per TB scanned via Storage Read API. An MV refresh scans BQ once — all subsequent matching queries hit Ontology DB at zero additional BQ cost.
⚠ Staleness trade-off
MV is only as fresh as the last refresh. Use REFRESH ASYNC EVERY (INTERVAL 1 HOUR) for near-real-time or REFRESH MANUAL for controlled windows. Live BQ fallback ensures correctness.
🔄 Transparent to BI tools
Tableau, Superset, Grafana connect once to Ontology DB with standard SQL — no awareness of whether results come from BQ or MV. Optimizer decides silently.
Step 1 — Create MV over BQ table (hourly)
Pre-aggregate namespace utilisation
CREATE MATERIALIZED VIEW mv_gke_namespace_util DISTRIBUTED BY HASH(namespace) BUCKETS 8 REFRESH ASYNC EVERY (INTERVAL 1 HOUR) AS SELECT namespace, DATE(start_time) AS dt, AVG(fraction) AS avg_util, MAX(fraction) AS peak_util, COUNT(*) AS samples FROM bq_np.gke_anpdev_np_us_east4_jpuv .gke_cluster_resource_usage GROUP BY namespace, DATE(start_time);
Step 2 — User query (unchanged)
Optimizer silently rewrites to use the MV
-- User writes against BQ table as normal SELECT namespace, DATE(start_time) AS dt, AVG(fraction) AS avg_util, MAX(fraction) AS peak_util, COUNT(*) AS samples FROM bq_np.gke_anpdev_np_us_east4_jpuv .gke_cluster_resource_usage WHERE start_time >= '2026-08-01' GROUP BY namespace, DATE(start_time); -- → Plan rewritten to scan mv_gke_namespace_util
Verify rewrite in EXPLAIN
OlapScanNode = MV hit; BigQueryScanNode = BQ call
EXPLAIN SELECT namespace, AVG(fraction) FROM bq_np.gke_anpdev_np_us_east4_jpuv .gke_cluster_resource_usage GROUP BY namespace; -- MV hit: OlapScanNode TABLE: mv_gke_namespace_util -- BQ call: BigQueryScanNode TABLE: gke_cluster_resource_usage
MV over BQ + JOIN with internal table
Cross-catalog rewrite also works
CREATE MATERIALIZED VIEW mv_enriched_util DISTRIBUTED BY HASH(namespace) BUCKETS 8 REFRESH ASYNC EVERY (INTERVAL 6 HOUR) AS SELECT b.namespace, b.fraction, c.team_owner, c.cost_centre FROM bq_np.gke_anpdev_np_us_east4_jpuv .gke_cluster_resource_usage b JOIN default_catalog.ops.cluster_config c ON b.cluster_name = c.cluster_name; -- Queries with this JOIN pattern hit the MV
Manual refresh & status check
Force refresh, monitor last state
REFRESH MATERIALIZED VIEW mv_gke_namespace_util; SELECT last_refresh_state, last_refresh_finished_time, last_refresh_error_message, rows FROM information_schema.materialized_views WHERE name = 'mv_gke_namespace_util';
Enable / disable rewrite per session
Force live BQ when freshness is critical
-- Use MV rewrite (default) SET enable_materialized_view_rewrite = true; -- Bypass — go direct to BigQuery SET enable_materialized_view_rewrite = false; -- See rewrite decision detail EXPLAIN VERBOSE SELECT namespace, AVG(fraction) FROM bq_np.gke_anpdev_np_us_east4_jpuv .gke_cluster_resource_usage GROUP BY namespace;

When to use MV rewrite with BigQuery

✓ Use it for
Dashboard / BI queries · Repeat aggregations · Cost-sensitive workloads · Offline resilience · Synapse / AN360 reporting layers
✗ Not suitable for
Real-time data (<1 min freshness) · Ad-hoc exploratory queries · Queries with user-specific filters not covered by MV
💡 Best practice
Define MVs at the granularity BI tools query (daily/hourly). Layer fine-grained MVs over coarse ones for multi-resolution dashboards.

JSON PIPE Loading — End-to-End Call Flow

What this gives you

Continuous, fault-tolerant loading of JSON and compressed JSON (.json.gz) files from GCS into Ontology DB — fully automated, no orchestration tool needed. The PIPE polls for new files, infers schema automatically (including concatenated JSON and files with raw control characters), and loads them in parallel batches. skip_error_files=true keeps the pipeline running through bad files rather than halting the entire load. max_error_count gives fine-grained control over fault tolerance. Designed for high-volume streams like Apollo alarm events, ECHO NOC events, and any GCS-backed data lake.
Enables: Apollo VSON Impact Assessment

File state machine

Apollo alarm format quirk

Concatenated JSON inside .json.gz

Files contain {obj1}{obj2}{obj3} — no newlines between objects, gzip-compressed.

Fix 1: Chunk-based read (not get_size). Compressed ≈ 5 MB, decompressed ≈ 50 MB — old code only read 10% of file.
Fix 2: iterate_many() handles adjacent objects natively — no separator needed.

Cross-Workspace Access (migration 110)

Any workspace owner can request read-only access to another workspace. On approval Catalyst executes GRANT SELECT ON ALL TABLES/VIEWS/MVs IN DATABASE <target> TO USER 'sa_<requester_slug>'@'%' on every cluster where both workspaces are ready. The SQL IDE sidebar and pipeline node editor both render granted external workspaces under a collapsible "External Workspaces" section. The pipeline lineage detector tags cross-workspace refs as cross_workspace_granted: true.

After provisioning, all workspace DB operations use sa_<slug>, never the cluster superuser. SA has full DML but no CREATE DATABASE and no catalog-level grants. Ontology DB — Catalog Ecosystem

What is an External Catalog?

An External Catalog lets Ontology DB query data in external systems without moving it. Users write standard SQL; Ontology DB pushes predicates, prunes columns, and reads data via the catalog's native API. Internal (native) tables live in default_catalog. All catalogs can be JOINed together in a single query.

Distance query — towers near a point
ST_DWithin for proximity search, ST_Distance for exact metres
-- Towers within 2 km of a given coordinate SELECT tower_id, region, ROUND(ST_Distance(location, ST_MakePoint(-73.935, 40.730)) / 1000, 2) AS dist_km FROM cell_towers WHERE ST_DWithin( location, ST_MakePoint(-73.935, 40.730), 2000.0 -- 2000 metres ) ORDER BY dist_km;
ST_ClusterDBSCAN — density-based clustering
Group nearby towers; noise (isolated towers) return NULL
-- DBSCAN: eps=500m, minpoints=3 SELECT tower_id, region, ST_ClusterDBSCAN(location, 500.0, 3) OVER (PARTITION BY region ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS cluster_id FROM cell_towers ORDER BY region, cluster_id NULLS LAST, tower_id; -- Count towers per cluster (exclude noise) SELECT region, cluster_id, COUNT(*) AS towers FROM ( SELECT region, ST_ClusterDBSCAN(location, 500.0, 3) OVER (PARTITION BY region ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS cluster_id FROM cell_towers ) t WHERE cluster_id IS NOT NULL GROUP BY region, cluster_id ORDER BY region, towers DESC;
ST_ClusterKMeans — fixed-k clustering
Partition towers into k groups using k-means++
-- Split each region into 4 clusters SELECT tower_id, region, ST_ClusterKMeans(location, 4) OVER (PARTITION BY region ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS cluster_id, ST_AsText(location) AS coords FROM cell_towers ORDER BY region, cluster_id; -- Centroid of each k-means cluster SELECT region, cluster_id, ST_AsText(ST_Centroid( ST_Envelope(ST_MakeLine( ST_MakePoint(MIN(ST_X(location)), MIN(ST_Y(location))), ST_MakePoint(MAX(ST_X(location)), MAX(ST_Y(location))) )) )) AS cluster_bbox_center FROM ( SELECT region, location, ST_ClusterKMeans(location, 4) OVER (PARTITION BY region ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS cluster_id FROM cell_towers ) t GROUP BY region, cluster_id;
